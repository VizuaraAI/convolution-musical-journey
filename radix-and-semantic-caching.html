Caching.

Chapter 12 of the book gives you prefix caching: hash a prefix, store its KV blocks, reuse them when the same prefix shows up again. This page is what comes next. SGLang's RadixAttention turns the cache into a tree so any matching prefix between any two requests can be reused. Continuous semantic caching goes one step further — it skips the engine entirely when a new query means the same thing as one already answered.

Two layers, one goal
query  →  semantic cache  →  radix tree  →  KV pages  →  decode
two chances to skip work — one by meaning, one by tokens.

Chapter 12 ends with the bonus that two users sharing a prefix share a cache hit. That bonus is leveraged once per request and only when prefixes match exactly. RadixAttention pushes that bonus to its limit; semantic caching argues that the limit is the wrong place to stop.

§ I

Why plain prefix caching is not enough.

Chapter 12's prefix cache hashes a prefix and reuses its K/V blocks. It works beautifully when the prefixes line up. The trouble is that, in real workloads, they often don't.

A vanilla prefix cache treats the cache as a flat hash table. When a new request arrives, the engine takes its prefix tokens, hashes them block by block, and walks the cache forward as long as each block hash matches. The first block whose hash is missing ends the match. Everything before is reused; everything after is recomputed from scratch.

This is enough for the easy case — the same system prompt across thousands of users. It is not enough for any workload that branches: tree-of-thought search, agentic loops, batched few-shot examples, or two chat sessions that share a system prompt but diverge in the second turn. Hashed prefix caching can only ride one prefix at a time. The moment two requests fork, you have two unrelated entries in the table.

The picture above is the entire motivation for the next chapter. We want a data structure that natively understands prefix relationships. When request A and request B share two blocks of prefix, that shared portion should live exactly once in the cache, and both requests should hang off its tail. That data structure is a radix tree.

§ II

RadixAttention — the cache as a tree.

SGLang's RadixAttention replaces the flat hash table with a radix tree. Tokens become path edges. Cached KV blocks live at the nodes. Prefix matching becomes a tree walk.

A radix tree is a compressed trie: each edge can carry a sequence of tokens (not just one). Every node represents a prefix that some past request has followed; the KV blocks for those prefix tokens are physically allocated and indexed by the node. Insertion and lookup walk the tree edge by edge, matching tokens until the input runs out or until an edge requires a token the input doesn't have.

Three operations matter. Lookup walks the tree from the root, matching token blocks against edges, returning the longest matched node. Insertion appends a new edge for the unmatched suffix. Eviction removes leaves under an LRU policy, recursively, when the GPU's KV memory budget is full.

Two important properties. First, any two requests that share a prefix automatically share KV blocks — no manual configuration, no per-template glue. Second, the tree structure lives on the CPU and is small (kilobytes); only the KV blocks themselves live in GPU memory, addressed via the page-table mechanism inherited from PagedAttention (Chapter 11).

§ IV

Four reuse patterns in the wild.

SGLang's authors point out that real LLM workloads almost always exhibit one of four prefix-sharing structures. Each one is a textbook reason RadixAttention exists.

The reported throughput numbers are dramatic. On Llama-7B and Mixtral-8x7B with these workloads, SGLang reaches up to 5× the throughput of vLLM and Guidance — not because the kernel is faster, but because so much prefill never has to run.

§ V

Where token-exact caching breaks.

RadixAttention is exact-prefix caching done as well as it can be done. There is still a wall: it can only reuse computation when prefixes are byte-equal.

Two queries that mean the same thing but are spelled differently — even just by a punctuation mark — produce different token sequences and therefore different cache keys. The radix tree sees no relationship between them. From a user-facing perspective, this is a missed cache hit; from the engine's perspective, it is doing the work it was built to do.

RadixAttention is not "wrong" here — token-equal prefixes is exactly the contract it is built on, and that contract is what makes it cheap and correct. Semantic caching is a different contract that lives at a different layer.

§ VI

Semantic caching — by meaning, not bytes.

A semantic cache stores answered (query, response) pairs indexed by the query's embedding. A new query is embedded and looked up by nearest-neighbour search. If a stored entry is close enough, the cached response is returned and inference never runs.

The picture is concrete. Embed every query into ℝᵈ with a small encoder. Pick a similarity threshold ε. The cache is a set of points (the queries that have been answered) with their responses attached. A new query is a point. If it lands within ε of a cached point, that's a hit and the engine returns the stored response. If not, the engine runs inference, stores the new (point, response) pair, and continues.

The economics are striking. A semantic-cache hit costs essentially nothing — one embedding, one nearest-neighbour query, no GPU inference. A semantic-cache miss costs whatever inference would have cost anyway, plus the small overhead of the embedding lookup. So as long as the hit rate is above any positive threshold, the average serving cost drops monotonically.

§ VII

The continuous-query problem.

Earlier semantic-cache designs assumed the world looks like a finite catalogue of queries with known arrival probabilities. In production, that assumption is false in a way that breaks the cache.

Real LLM queries do not come from a discrete list. They come from a continuous, infinite-dimensional embedding space, and their distribution drifts day by day as users, products, and prompts change. You will never see the same sequence of bytes twice. The cache cannot enumerate the universe; it has to generalize over it.

Two questions become first-class. Which neighbourhoods of embedding space are worth caching? — because some regions are dense with queries and high-cost answers, others are sparse and cheap. How do we decide under uncertainty? — because we only ever see partial feedback (the cost of the queries we actually answered), never the full cost surface.

§ VIII

Dynamic ε-nets and online learning.

The Atalar-et-al. framework's central trick is to discretize the continuous embedding space with a dynamic ε-net, then estimate the cost surface across each cell with kernel ridge regression. This connects the discrete cache literature to the continuous query reality with a clean theoretical bridge.

An ε-net is a finite set of "anchor" points in embedding space such that every other point is within ε of at least one anchor. As queries arrive, the system maintains such a covering and treats each anchor's neighbourhood as a single cache cell. The cost of a query in cell c is estimated by KRR over the queries observed in and near c, with a quantified uncertainty: cells with few observations get a wider confidence interval and the algorithm explores them; cells with tight estimates and high estimated cost are committed to the cache.

Two practical consequences. The cache adapts when query patterns drift — a region that becomes hot is detected and its cells become cached. Switching costs are explicitly accounted for, so the algorithm doesn't churn the cache on every minor shift.

"Sublinear regret" is the same theoretical promise that bandit algorithms make: the long-run average cost of the algorithm approaches the cost of the best fixed strategy you could have chosen with hindsight. Here, that "best fixed strategy" is the optimal cache layout under the true continuous query distribution.

§ IX

The two-tier architecture.

Semantic caching and RadixAttention are not alternatives. They live at different layers and answer different questions. A modern serving stack ships both.

An important practical detail: the semantic cache is response-level caching, so it is only safe for queries that are deterministic, idempotent, and not personalized. Customer-specific lookups, time-sensitive questions, anything with sampling temperature greater than zero — those have to bypass tier 1 and go straight to tier 2. Production systems often gate semantic caching behind a tag or a query-classifier, and let RadixAttention be the always-on path.

Where this fits in the book.

Chapter 12 introduces prefix caching as the foundation. RadixAttention is the data-structure upgrade that lets prefix caching work across unrelated requests, not just within a session — it is the engine-layer gem that makes SGLang outperform vLLM on tree-search and agentic workloads (Chapter 20). Continuous semantic caching, in turn, sits one layer above the engine entirely: a request-router decision, made before the model is loaded for a given query at all. Both are caching ideas; both are about doing less work; both are extensions of the bonus that Chapter 12 ends on.
