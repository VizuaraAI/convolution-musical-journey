Why Both Memory AND Compute Matter

Two Resources, One Bottleneck

During inference (autoregressive generation), each new token requires two things:

1
Memory to store past context (KV cache or recurrent state). This grows with every token generated and determines how many sequences you can serve concurrently.
2
Compute to process the new token against all past context. This determines how long each token takes to generate — and whether latency degrades at long sequences.

At short sequences, neither is a problem. At long sequences (100K+ tokens), both become bottlenecks. Different techniques optimize different dimensions. Some reduce memory, some reduce compute, some reduce both.

The quality gap SSMs can't fully close. Mamba and linear attention achieve constant memory and compute — but attention's ability to do exact token-to-token lookup (e.g., "what was the 3rd item in the list?") is something lossy state compression fundamentally struggles with. This is why the best production models (Jamba, DeepSeek) use hybrid architectures: a few attention layers for precise retrieval + many SSM/linear layers for efficient long-range context.

Where SSMs Fall Short

In-Context Learning

Transformers can learn new tasks from examples in the prompt. SSMs struggle here — fixed-size state can't store arbitrary input-output mappings the way attention over raw tokens can.

Exact Retrieval

"Copy the 5th word" or "What was the phone number?" require precise lookup. Attention does this trivially. SSMs compress past tokens into a fixed state — individual tokens may be irrecoverable.

Multi-hop Reasoning

"A is B, B is C, therefore A is C" requires holding multiple facts and combining them. The lossy compression of SSM state makes chaining inferences harder than with full attention.

Hardware Ecosystem

Transformers have years of GPU kernel optimization (FlashAttention, PagedAttention, etc.). SSM kernels are newer and less mature, meaning theoretical FLOPs advantages don't always translate to wall-clock speedups.

During decode, each new token's query must attend to all past keys and values. Recomputing them every step would be wasteful, so we cache the K and V projections from every previous token.

Compute — The FLOPs Problem

2.1 — Why FLOPs Matter for Inference

During decode, generating each new token requires computing attention scores against all past keys. The per-token decode cost for attention:

FLOPs per token = 2 × N × d   (dot product with N keys + weighted sum of N values)

At N=100K with d=2048, each new token costs ~410M FLOPs just for attention. And it gets worse with each token generated — because N keeps growing.

2.8 — Does Compute Actually Matter for Inference Latency?

Yes — but the real story is more nuanced.

During prefill, compute is parallelized across all tokens. During decode, computation is sequential: one token at a time, each must complete before the next starts. So decode latency per token is proportional to FLOPs per token.

But here is the critical insight. At N=100K with full attention:

Compute Time

~4 μs

410M FLOPs at 100 TFLOPS

Memory Read Time

~390 μs

781 MB KV cache at 2 TB/s

The memory read takes ~100× longer than the compute. Decode is fundamentally memory-bandwidth bound, not compute bound.

Key insight: Decode is memory-bandwidth bound, not compute bound. This is why MQA/GQA (which reduce memory reads) can speed up inference more than reducing FLOPs alone. Reducing the KV cache size means fewer bytes to read from HBM, directly reducing per-token latency.

That said, for very long sequences, both matter. And for throughput-constrained scenarios (many concurrent users), memory capacity determines how many requests you can batch together.

The DeepSeek-V2 insight. Despite being 236B parameters, DeepSeek-V2's MLA compresses each token's KV representation into a single 512-dim vector (vs. Llama's 2048-dim with GQA). That's a 4× reduction — making a 236B model's KV cache smaller than a 70B model's. MLA achieves this by learning a low-rank compression of keys and values, then reconstructing full attention heads on-the-fly during decoding.

Key Takeaway: Memory

At 100K tokens, pure MHA models become impractical. GQA, MLA, and sliding windows make long-context feasible. Mamba/hybrid architectures make it trivial.

Key Takeaway: Compute

Full attention's O(Nd) decode cost means ~410M FLOPs/token at N=100K. Sliding window caps this at ~16.8M. SSM/Mamba: ~2.7M — 150× cheaper than full attention.

Memory and compute are two sides of the same coin. The best inference systems optimize both — using GQA to shrink the KV cache, sliding windows to cap compute, and increasingly, hybrid architectures that combine a few attention layers (for precise recall) with Mamba layers (for efficient long-range context). DeepSeek-V2's MLA shows that clever compression can give you near-MHA quality at a fraction of the memory cost.
