Step 1

Start by constraining the problem.

Do not jump straight to GPUs. The correct architecture depends on workload shape.

Clarifying questions

  1. What model sizes are we serving: 8B, 70B, MoE, or multiple tiers?
  2. What are prompt and output length distributions, not just averages?
  3. What are the SLOs: TTFT, ITL, total latency, and availability?
  4. Is traffic streaming chat, agents, tool calls, batch jobs, or mixed?
  5. How strict are structured output, safety, privacy, and audit requirements?
  6. How much traffic is bursty, regional, or tenant-isolated?
Good interviewer signal: show that "millions of requests" is not enough. Tokens/sec, context length, output length, and P99 SLO decide the design.

Step 3

The serving engine is where course optimizations compose.

PagedAttention

Stores KV cache in blocks, avoids contiguous allocation waste, and enables high concurrency.

Continuous batching

Admits new requests each decode step so finished sequences do not leave the GPU idle.

Chunked prefill

Breaks long prompts into pieces so prefill does not starve decode.

Prefix caching

Reuses KV for shared system prompts, histories, and document prefixes.

Quantization

Reduces weight bandwidth and memory footprint, with quality checks before rollout.

Speculative decoding

Uses a small draft model to reduce large-model forward passes when acceptance rate is high.

Scaling: replicate for throughput, tensor-parallelize when one model replica does not fit or needs more bandwidth, pipeline-parallelize only when crossing nodes is unavoidable, and use disaggregated serving when long prefill bursts interfere with decode SLOs.

Final script

A complete interview answer.

I would first characterize the workload by prompt length, output length, request rate, concurrency, streaming requirements, and SLOs for TTFT, inter-token latency, total latency, and availability. Millions of requests is not the sizing unit; tokens/sec and context-length distribution are.

The architecture starts with a regional edge and API gateway for auth, quotas, rate limits, request shaping, and input safety checks. Behind that I would use a smart inference router. It chooses the model tier, decides online vs batch, applies canary traffic rules, and routes cache-sensitive requests to replicas that already hold useful prefix KV state.

For the online serving engine I would use a vLLM or TensorRT-LLM style runtime with PagedAttention for KV memory management, continuous batching for throughput, prefix caching for repeated prompts, chunked prefill to protect decode, and speculative decoding where the draft acceptance rate is high. I would quantize only after evals show quality holds.

For large models I would replicate model instances for throughput, use tensor parallelism inside high-bandwidth NVLink domains, and only use pipeline parallelism across nodes when model capacity forces it. If traffic has many long prompts, I would split prefill and decode pools so compute-heavy prefill does not disrupt memory-bandwidth-bound decode. I would account for the KV transfer tax before choosing disaggregation.

I would separate batch workloads from realtime traffic. Batch jobs can queue for high GPU utilization, but online decode should not wait behind offline summarization or eval workloads. Under overload I would use admission control, lower-tier fallback, shorter max output, or async handoff depending on product requirements.

Every release goes through offline evals, shadow traffic, canary rollout, and rollback gates. The dashboard tracks TTFT, ITL, total latency, queue depth, GPU utilization, VRAM, KV cache hit rate, output-token distribution, schema validity, safety flags, and cost per request. The main trade-off is latency versus utilization: batching, caching, and routing are how I choose that trade-off per request class instead of globally.
