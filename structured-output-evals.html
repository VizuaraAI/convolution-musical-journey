Reliability starts at the token boundary.

Production inference is not complete when the model emits fluent text. Many products need valid JSON, safe tool calls, stable business fields, and measurable quality across releases.

Part 1

JSON schema turns language into a contract.

A schema states the shape of the answer the application expects. The model may still reason in text internally, but the serving boundary should return typed fields.

{
  "type": "object",
  "required": ["invoice_id", "total", "currency", "risk_flags"],
  "properties": {
    "invoice_id": {"type": "string"},
    "total": {"type": "number"},
    "currency": {"enum": ["USD", "EUR", "INR"]},
    "risk_flags": {"type": "array", "items": {"type": "string"}}
  }
}
Key distinction: a prompt asks politely. A schema constrains the application contract. Guided decoding is how that contract reaches the token sampler.
Part 2

Guided decoding masks impossible next tokens.

At each generation step the decoder has a vocabulary distribution. A grammar or finite-state machine removes tokens that would make the output invalid. For a JSON object, after {"currency": ", the only valid continuations might be USD, EUR, or INR.

Free decoding

model logits:
  "USD" 0.30
  "dollars" 0.28
  "N/A" 0.14
  "\n" 0.08
result: may be invalid

Guided decoding

valid token mask:
  "USD" allowed
  "EUR" allowed
  "INR" allowed
  everything else = -infinity
result: syntactically valid
MethodUse it forTrade-off
Logit biasingEncourage or discourage specific tokensSoft control, not a guarantee
JSON modeWell-formed JSONMay not enforce your exact schema
Grammar-guided decodingStrict structured outputMore sampler overhead
Post-parse repairFallback for malformed outputAdds latency and can hide regressions
Part 3

An eval harness is production CI for behavior.

Unit tests tell you if code still runs. Evals tell you if model behavior still works. For structured output, evaluate syntax, field-level correctness, semantic correctness, safety, latency, and cost.

Minimal eval record

example_id: invoice_042
input: scanned invoice text
expected:
  invoice_id: INV-2026-042
  total: 1287.50
  currency: USD
checks:
  parse_json == true
  schema_valid == true
  exact(invoice_id)
  abs(total - expected.total) < 0.01
  currency in allowed_enum
  p99_latency_budget_ms < 1200

Golden sets

Curated examples with known expected outputs. Small, high quality, reviewed by humans.

Synthetic sets

Generated variations to stress formats, edge cases, languages, and long contexts.

Production samples

Anonymized real traffic to catch drift and mismatches between evals and reality.

Do not only use judge models. Deterministic checks should catch parse validity, schema validity, enums, numeric tolerances, citation existence, and tool argument shape before any LLM judge is involved.
Part 4

Benchmark the system, not just the model.

A benchmark should separate queue time, tokenization, prefill, first-token latency, inter-token latency, post-processing, guardrail time, and network overhead.

MetricQuestion it answers
Queue timeIs demand exceeding scheduler capacity?
Prefill timeAre prompts too long or cache hits too low?
TTFTHow quickly does the user see progress?
ITL / TPOTIs decode rhythm smooth?
Validation timeAre guardrails or repair loops dominating?
Cost/requestDid output length or model routing drift?
Final lesson: schema, evals, and latency profiling are part of inference engineering because they decide whether a faster system is actually shippable.
